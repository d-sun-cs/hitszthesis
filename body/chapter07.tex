\chapter{预计困难及解决方案}

\section{预计困难与技术难点}

本课题的主要困难与技术难点包括：

\begin{itemize}
    \item Ceph作为发展许久的社区开源项目，内容庞大且复杂，其中纠删码接口位于顶层应用与底层IO之间，解析所有相关函数接口及参数含义需要较大工作量。
    \item Ceph大型真实分布式集群的环境难以搭建与调试，容易陷入大规模集群维护的困境中，且在物理机完整地从源码编译Ceph需要繁琐地环境配置与等待，费时费力，不利于课题核心优化方案的研究。
    \item Ceph的纠删码接口只会给数据块和校验块申请大小相同的内存空间，然而Shift-XOR纠删码的校验块的长度会比数据块大常数级别的大小，在接口内申请额外内存又会导致Ceph的内存管理报错。
    \item Two-tone纠删码在实现时数据块与校验块的访问模式差异大，泛化解码与重编码的流程复杂，难以形成统一的高局部性内存访问策略，需要突破内存瓶颈。
\end{itemize}

\section{解决方案}

针对上述难点，拟采取如下解决措施：

\begin{itemize}
    \item 借鉴Ceph中已经集成好的其他纠删码的实现组织形式，先模仿出一个最简的可运行的自定义纠删码，再逐步丰富；解析Ceph提供的纠删码接口测试脚本，确定有哪些重要功能需要被测试，从而指导接口功能的实现。
    \item Ceph的特定版本如v18.2.7提供了容器环境的配置方案，可直接在开箱即用的容器中编译Ceph，并且可保留容器环境用于进一步测试。
    用Ceph提供的vstart脚本在单机容器内启动多节点虚拟集群，功能同样完善，无需过度担心环境问题。
    \item 将校验块更长的一小部分数据存储到内存数据库Redis中，看作Ceph集群管理的元数据之一，由于多出的数据只是常数级别大小，且存储于内存中，对这部分数据的访问几乎不影响纠删码本身的编码和解码性能。
    \item 关于Two-tone系统级优化难点的解决方案，第2章的研究方案中已经做出了充分地阐述，即设计抽象结构、划分数据增加局部性和合并访问内存等方案。
\end{itemize}
